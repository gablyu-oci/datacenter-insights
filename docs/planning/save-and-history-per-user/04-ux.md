# 04 — UX: Per-User `insight_subscription` + Collapsed-Count Fix

- **Owner:** Product Design
- **Status:** Draft, ready for engineering
- **Date:** 2026-05-21
- **Surface:** AI Insights tab — `SavedInsightsSection`, `PastRunsSection`, the shared `Collapsible` component
- **Inputs:**
  - `docs/planning/save-and-history-per-user/01-PRD.md`
  - `docs/planning/save-and-history-per-user/02-research.md`
  - `docs/planning/save-and-history-per-user/03-architecture.md`
  - `docs/planning/save-and-history/04-ux-design.md` (original Save + Past Runs UX — vocabulary baseline)

This is a small UX-correctness pass on the existing sidebar. There is no layout
redesign, no new affordance, no new icon. The work is: (a) make the Saved list
honest about ownership, and (b) make the collapsed count badge stop lying.

---

## 1. Context & Problems

Two distinct user-trust problems on the AI Insights tab today, both small in
surface area but corrosive to confidence in the feature:

**Problem A — Cross-user leakage of saved items.** `insight_subscription` is
globally shared. When Gabrielle saves an insight, it appears in Karan's
sidebar the next time he opens the tab. This is not a security issue (we are
behind oauth2-proxy + IDCS, everyone is a logged-in Oracle employee), it is a
clarity + trust issue: the Saved list reads as a personal shortlist but
actually behaves like a shared mailbox. Users reasonably assume "Saved"
means "mine."

**Problem B — Collapsed sections show a misleading `(0)`.** The Saved and
Past Runs section headers are collapsed by default and fetch their lists
lazily on first expand. Until the user expands, `count` resolves to `0` and
the header renders `Saved insights (0)` — which reads as "you have nothing
saved" even when the underlying data has 7 rows. We have direct user
reports of "this looks broken, there's nothing here." The collapsed state
should never assert emptiness it cannot back up.

---

## 2. Design Principles for This Change

1. **Truthfulness over precision.** Never display a count that contradicts
   reality. A pending state ("loading") is a perfectly fine answer; a wrong
   number is not.
2. **Loading is honest.** The pending state is shown explicitly (`(…)`), not
   masked as `(0)`.
3. **No new affordances.** This is a polish pass. No new buttons, toggles,
   icons, or sections.
4. **Per-user scope is invisible when it works.** A correctly-implemented
   per-user Saved list should feel like nothing changed for the single user
   — their saves "just work." The behavioral difference is only observable
   across users.
5. **Past Runs stays shared.** Sessions are the team's source of truth; the
   sidebar must not falsely imply per-user ownership of the runs list.

---

## 3. Sidebar State Matrix

Applies to both `SavedInsightsSection` and `PastRunsSection` via the shared
`Collapsible` component. "Badge" = the parenthesized text after the section
title. "Body" = what renders inside the expanded region.

| # | Scenario | Badge content | Badge ARIA label | Section header text | Body content |
|---|---|---|---|---|---|
| 1 | Initial mount, counts endpoint in flight | `(…)` | `Loading count` | `Saved insights` / `Past runs` | (not rendered — section collapsed) |
| 2 | Counts loaded, value is `0` | `(0)` | `0 saved insights` / `0 past runs` | unchanged | (not rendered — collapsed) |
| 3 | Counts loaded, value is `N > 0`, section collapsed | `(N)` | `N saved insights` / `N past runs` | unchanged | (not rendered — collapsed) |
| 4 | Section expanded, list endpoint in flight | `(N)` (or `(…)` if counts also still loading) | as above | unchanged | Skeleton rows (existing `SkeletonCards` / `SkeletonRows`) |
| 5 | Section expanded, list returned empty | `(0)` | `0 saved insights` / `0 past runs` | unchanged | Empty-state block (copy in §6) |
| 6 | Section expanded, list returned items | `(N)` | `N saved insights` / `N past runs` | unchanged | Existing card / row layout |
| 7 | Error fetching counts | no badge | (no element rendered; nothing to announce) | unchanged | (collapsed body, not rendered) |
| 8 | Error fetching list (after expand) | last-known badge value (or no badge if counts also failed) | as last known | unchanged | Existing `InlineError` block (copy in §6) |

Notes:

- Row 7 is the key correctness rule: **when counts cannot be fetched, render
  no badge at all** rather than fall back to `0`. The existing Collapsible
  already supports this — `count={null}` hides the badge (`Collapsible.tsx`
  lines 68–72, 123).
- Row 4: it is possible for the list refetch to happen after the counts
  endpoint already resolved. In that case the badge keeps the cached number;
  it does not flicker back to `(…)`.
- Row 5 (`(0)`) is the one legitimate place `(0)` shows: the section is
  expanded, the user can see the empty-state copy, and the badge agrees with
  the body. No deception.

## 4. Badge / Pill Copy Spec

Maps directly onto the `Collapsible` component's existing `count` /
`countPending` props (`Collapsible.tsx:30–41`). No new props.

| Logical state | `count` prop | `countPending` prop | Rendered text | Tooltip / ARIA |
|---|---|---|---|---|
| Counts loading (pre-resolve) | `null` | `true` | `(…)` | aria-label on badge span: `Loading count` |
| Counts resolved, value `0` | `0` | `false` | `(0)` | aria-label: `0 saved insights` (or `0 past runs`) |
| Counts resolved, value `N > 0` | `N` | `false` | `(N)` | aria-label: `N saved insights` (or `N past runs`) |
| Counts endpoint errored | `null` | `false` | (no badge rendered) | none — element absent; tooltip on header itself reads `Count unavailable` (see §8) |

Implementation note for engineering: the existing Collapsible already
distinguishes `count = null` (hide badge) from `count = 0` (show `(0)`), so
no component change is required to support the error case — the consumer
hook just needs to pass `null` when its fetch errors.

Truthfulness rule restated: **`(0)` is only acceptable when the counts
endpoint has successfully returned `0`.** Anything else — pre-fetch,
in-flight, errored — must render either `(…)` or nothing.

## 5. Section-by-Section UX

### 5.1 Saved insights — now per-user

**Behavioral change (user-visible):** the list reflects only the current
user's saves. After deploy, Gabrielle keeps her existing saves (backfilled
via migration). Karan and other stakeholders start with an empty list and
build their own.

**No new UI for per-user scope.** We deliberately do NOT add:
- a "yours / shared" toggle (out of scope — there is no shared mode anymore),
- an account chip in the section header (the global `UserMenu` in the app
  header already conveys identity),
- visible owner attribution on saved cards (each card is implicitly the
  viewer's; no other user's saves are reachable from this surface).

**Empty-state microcopy options** (pick one in implementation; current copy
already reads well — option B is the recommended default since it matches
the existing string):

- **Option A** (explicit personal framing): `No saved insights yet — bookmark any insight from the main view to see it here.`
- **Option B** (existing copy, retained): `No saved insights yet — tap the bell on any insight to save it.`

Recommendation: keep **Option B** to minimize churn; the per-user nature
of the list is conveyed by the section's behavior, not its empty-state
copy.

### 5.2 Past runs — remains shared

The Past Runs list intentionally stays shared across the team (PRD §3.2,
architecture ADR-6). The daily AI-insights cron emits one session per day
that everyone sees — that is the team's shared source of truth.

**The section header must not imply per-user ownership.** Specifically:

- Do NOT rename the section (it stays `Past runs`).
- Do NOT add "your" / "my" framing in the header or empty state.
- Empty-state copy is unchanged: `No past runs yet — kick off an AI session to see history here.`

Optional (defer to PM): add a one-line tooltip on the Past Runs section
header — see §8.

## 7. Auth-Failure UX (401 in Production)

The PRD/architecture allows for a production-only failure mode: the
`X-Forwarded-Email` header is unexpectedly missing (oauth2-proxy
misconfiguration, session expiry, etc.), and the backend returns
`401 missing_x_forwarded_email` on `/api/insights/counts`,
`/api/insights/saved`, and the subscribe endpoints. The dev fallback to
`dev@local` is NOT in play in prod.

**UX behavior:**

1. **Sidebar continues to render.** The rest of the AI Insights tab —
   `SnapshotInsightFeed`, charts, citations — does not depend on
   per-user identity and stays fully functional. A user who somehow lost
   their session can still read the latest insights.
2. **Saved section badge → no badge.** Per §4, the counts hook treats
   any error (including 401) as "render `null`." No misleading `(0)`.
3. **Past Runs section badge → also no badge** if the combined counts
   endpoint fails. The Past Runs list itself does not require identity
   to fetch (sessions are shared), but the count is bundled into the
   same `/api/insights/counts` request that 401s. Acceptable: better
   to drop both badges together than to show one and not the other.
4. **Saved section, on expand → inline error.** The expanded body shows
   the existing `InlineError` block with the auth-flavored copy:
   `Couldn't load your saved insights — try refreshing or signing in again.`
   The `Retry` button re-issues the failing fetch.
5. **Past Runs section, on expand → still works.** The
   `/api/insights/sessions` endpoint does not require identity, so the
   list renders normally even while `/counts` is 401-ing. Slight
   asymmetry (no badge, working list), but it is honest.
6. **No global error banner, no modal, no redirect.** The user may not
   be ready to re-authenticate at that moment; we do not interrupt
   their reading.

The 401-specific message in the Saved error is the only place in this
change where we exposed an auth-related string. Everywhere else we
remain auth-agnostic.

## 8. Microcopy: Optional Tooltip on Section Headers

Optional addition; both strings marked OPTIONAL for PM to accept or drop.
Render as `title=""` attribute on the section header `<button>` (no
custom tooltip component needed; native browser tooltip is sufficient
for a stakeholder-only tool).

| Section | Suggested tooltip string | Status |
|---|---|---|
| Saved insights | `Your personal bookmarks — only you can see this list.` | OPTIONAL |
| Past runs | `Daily runs are shared across the team.` | OPTIONAL |

Design lean: ship neither, lean on the behavior to speak for itself. If
either is shipped, ship both together so the per-user/shared distinction
reads as a coherent choice rather than a one-off label.

In the error-counts case (§4 row 7, §7), the Saved header's tooltip
should read `Count unavailable` instead of the personal-bookmarks
copy. The Past Runs header's tooltip should similarly fall back to
`Count unavailable` when its count failed.

## 9. Accessibility Notes

The existing `Collapsible` ARIA shape is preserved verbatim
(`Collapsible.tsx:82–135`):

- Section header `<button>` keeps `aria-expanded`, `aria-controls`, and
  `aria-label` (`Expand <title>` / `Collapse <title>`).
- Section body keeps `role="region"` with `aria-labelledby` pointing at
  the header id.
- The count badge keeps `aria-live="polite"` so the screen reader
  announces the transition from `(…)` to `(N)` once it resolves.

Additional screen-reader behavior for the new pending / error states:

| State | Screen-reader announcement |
|---|---|
| Pending counts | The badge text `(…)` is announced; supplement with `aria-label="Loading count"` on the count span so AT speaks `"Loading count"` rather than literally "left-paren ellipsis right-paren." |
| Real count loaded | The live-region announces the new text, e.g. `"7"` or `"0"`. Pair with an `aria-label` on the badge span — `"{N} saved insights"` / `"{N} past runs"` — so the count has a unit attached when read in isolation. |
| Error — no badge | Badge element is omitted entirely. There is no aria-live announcement. The section header still announces normally on focus (`Expand Saved insights`). The optional tooltip `Count unavailable` is exposed via the header button's `title` attribute, which most screen readers will announce as a tooltip on focus. |
| Auth-failure inline error | The existing `InlineError` block already carries `role="alert"` (`SavedInsightsSection.tsx:153`), so the new auth-flavored copy is announced immediately on expand. No change to the alert role. |

Keyboard behavior is unchanged from V1:

- Tab order: section header → (if expanded) row buttons / cards / Save buttons → next section header.
- `Enter` / `Space` toggles the header; focus stays on the header per V1 spec.
- The `Retry` button inside `InlineError` is keyboard-reachable on expand.

Color contrast: the "no badge" state cannot fail contrast (nothing
rendered). The `(…)` pending state uses `tokens.color.text.faint` per the
existing Collapsible; if that token is below 4.5:1 against
`tokens.color.bg.page`, prefer `tokens.color.text.caption` as the
fallback. Engineering to verify against the audit doc.

## 10. Out of Scope (Explicit)

Mirroring PRD §3.2, §9 and architecture §12:

- No layout redesign of either section.
- No admin / superuser "all users' saves" view.
- No sharing affordances (transfer, share, see-someone-else's-list).
- No change to Past Runs scoping — sessions stay shared, the count
  stays a global count.
- No new icon, new pill, new chip, or new section.
- No deep-linking to a specific saved insight via URL.
- No per-user notes / tags / folders on saved items.
- No "owner" attribution rendered on insight cards.
- No styling work on the `UserMenu` component already in this branch
  (covered separately).

## 11. Acceptance — Design QA Checklist

A designer or QA can walk this manually in 5 minutes against a staging
deploy. Any "no" on any line blocks ship.

- [ ] Open the AI-Insights tab from a cold load (hard refresh).
      **Both** the Saved insights and Past runs section headers show
      `(…)` momentarily, then resolve to real numeric counts within
      ~1 second. The badges do NOT flash `(0)` at any point.
- [ ] Click the bell on an insight in the latest snapshot to save it.
      The Saved insights badge increments by 1 without manual refresh,
      and on expanding the section the new card is present.
- [ ] Click the filled bell on a saved card to unsave it.
      The Saved badge decrements by 1; the card fades out; the count
      does not desync from the list.
- [ ] Open the tab as a second user (different `X-Forwarded-Email`
      identity — easiest path is a second oauth2-proxy session in an
      incognito window). The Saved badge reflects only that user's
      saves. Nothing the first user saved appears.
- [ ] The Past Runs badge is identical across users (sessions are
      shared). Confirm both users see the same N.
- [ ] Network panel: kill the `/api/insights/counts` request (block in
      DevTools). On next tab mount, neither section renders a count
      badge; no `(0)`; no JS error. Expanding either section still
      works (Past Runs list renders normally; Saved shows the
      auth-flavored inline error if the underlying list also fails,
      otherwise loads cleanly).
- [ ] Production simulation: ask backend to drop `X-Forwarded-Email`
      and confirm /counts returns 401. Sidebar handles gracefully per
      §7 — no badges, Saved inline error reads `Couldn't load your
      saved insights — try refreshing or signing in again.`, Past
      Runs list still works.
- [ ] Screen-reader smoke (NVDA or VoiceOver): focus on each section
      header. The pending state announces as `Loading count` (not
      `dot dot dot`). Real counts announce as `7 saved insights`,
      `12 past runs`. Error state header announces `Count unavailable`
      via the title tooltip (if the optional §8 tooltip ships) or no
      count announcement at all (if §8 deferred).
- [ ] `prefers-reduced-motion: reduce` enabled: chevron rotates
      instantly, no transition. Card fade-out on unsave is instant.
      No regressions vs V1.

## 12. Summary of UX Decisions

1. **`(0)` is acceptable only when the counts endpoint successfully
   returned 0** — never as a placeholder for "haven't fetched yet" or
   "fetch errored."
2. **Pending counts render as `(…)` with ARIA `Loading count`.**
3. **Errored counts render nothing — no badge, no fake number.**
   The optional `Count unavailable` tooltip on the header can carry the
   explanation if PM wants it.
4. **Per-user Saved scope is invisible at the UI surface.** No new
   chips, toggles, or owner labels — the list just contains the right
   rows for the right user.
5. **Past Runs stays shared and the UI does not claim otherwise.**
   No "your runs" framing; optional tooltip `Daily runs are shared
   across the team.` is available if PM wants explicit reassurance.
6. **401 in prod degrades gracefully:** no badges, Saved section shows
   an auth-flavored inline error on expand, rest of the tab keeps
   working.
7. **No layout, no new tokens, no new icons, no new components.** The
   existing `Collapsible` props (`count`, `countPending`) already
   support every state in §3.

End of UX doc.
